# Muse 单图链路改造确定版清单

> 本文档是在 `推荐链路设计.md` 基础上的收敛版本。目标不是继续讨论方向，而是明确本次改造的确定决策、实施边界、阶段顺序和文件级修改清单，作为后续实际开发的执行依据。

---

## 1. 本次改造的确定目标

本次改造明确只做一件事：

**把当前“批量 10 张 + 整批预加载 + 每张提交后同步拉统计”的链路，改成“单图任务分配 + 最多预取 1 张 + 图片直连对象存储 + 统计弱同步”的链路。**

本次改造完成后，用户主链路应变为：

1. 用户点击“开始”
2. 前端请求 `/api/tasks/next`
3. 后端返回 1 个当前任务
4. 浏览器直接请求对象存储/CDN 图片地址
5. 前端在后台最多再请求 1 个 `nextTask`
6. 用户提交评分到 `/api/tasks/{task_id}/submit`
7. 提交成功后立即切到 `nextTask`
8. 统计信息本地乐观更新，后台定时校准

---

## 2. 已确定的设计决策

以下决策在本轮不再作为开放选项讨论，默认按此执行。

### 2.1 图片仍然直连对象存储/CDN

确定：

1. 图片文件不经过业务后端中转
2. 后端只返回图片元数据和可访问 URL
3. 前端 `img.src` 直接使用对象存储/CDN 地址

原因：

1. 当前图片慢的主要问题不在业务后端代理
2. 真正问题在于前端批量预取过多原图
3. 保持直连可减少后端带宽和复杂度

### 2.2 本次引入任务分配表

确定新增 `annotation_tasks` 表。

不再依赖：

- `images.score_count = 0` 直接取一批图

改为：

- 先分配任务
- 再基于任务提交结果

原因：

1. 单图模式下没有任务层会很难处理并发与过期
2. 预取下一张本质上也是“先领取一个任务”
3. 后续复标、过期回收、审计都依赖任务层

### 2.3 本次保留 Redis 异步落库链路

确定保留当前：

- `/submit` -> Redis queue -> worker -> PostgreSQL

原因：

1. 这部分不是当前首要性能瓶颈
2. 已有代码和运维路径都围绕它展开
3. 本轮重点应放在取图链路、前端状态和任务分配

### 2.4 本次数据库同时保存 `object_key` 和 `public_url`

确定：

1. `images` 表新增 `object_key`
2. 保留 `public_url` 字段
3. 旧 `r2_url` 逐步迁移为 `public_url`

原因：

1. 直接彻底移除 URL 会增加切换成本
2. 保留 URL 可以降低后端改造初期风险
3. `object_key` 为将来切换域名、签名 URL、缩略图派生保留空间

本轮实际策略：

1. 后端优先返回 `public_url`
2. `public_url` 为空时，按 `object_key + R2_PUBLIC_URL` 拼接

### 2.5 本次前端最多持有 2 个任务

确定同一时刻前端最多只有：

1. `currentTask`
2. `nextTask`

不允许：

1. 缓存 3 张及以上待标注图片
2. 并行预加载多张原图
3. 再使用 `images[]` 批次模型驱动主流程

### 2.6 预取下一张会占用一个真实任务

确定：

1. `nextTask` 不是纯前端占位符
2. 它是后端实际分配出来的任务
3. 若用户离开页面，该任务通过 `expires_at` 回收

原因：

1. 这样切图才能真正做到“提交成功后立即切换”
2. 若不真实分配，后续仍会在切图时等待接口返回

控制约束：

1. 每个用户最多允许 2 个活跃任务：当前 1 个 + 预取 1 个
2. 活跃任务超限时，`/api/tasks/next` 优先返回已有未提交任务，而不是继续发新任务

### 2.7 统计走弱同步

确定：

1. 提交成功后，前端本地 `total_scores += 1`
2. 前端本地 `today_scores += 1`
3. 后台每 60 秒校准一次 `/api/my-stats`

不再做：

1. 每次提交完都立即调用 `/api/my-stats`

### 2.8 本轮不做缩略图系统

确定：

1. 本轮先不引入预览图/原图双轨字段
2. 先通过“单图 + 只预取 1 张”解决主要问题

原因：

1. 这是明显更小、更稳妥的第一步
2. 如果切换后仍慢，再进入第二轮做图片尺寸优化

## 3. 不在本轮范围内的事项

以下内容明确不纳入这一轮改造：

1. 管理后台大改版
2. 评分维度变化
3. 多轮复标策略
4. 图片审核流
5. 缩略图生成服务
6. 签名 URL 鉴权
7. Alembic 等迁移框架引入

说明：

当前仓库没有迁移框架，且 `backend/main.py` 中的 `Base.metadata.create_all()` 不能自动修改已有表结构，因此本轮数据库变更采用手工 SQL 迁移脚本或直接更新 `sql/schema.sql` + 线上手动执行的方式推进。

## 4. 数据库确定改动

### 4.1 `images` 表调整

确定改动：

1. 新增 `object_key TEXT`
2. 新增 `public_url TEXT`
3. 新增 `status VARCHAR(16) DEFAULT 'pending'`
4. 保留 `score_count`
5. 保留 `deleted`
6. 保留旧 `r2_url` 作为过渡字段，但新代码不再优先依赖它

状态枚举在本轮固定为：

- `pending`
- `assigned`
- `completed`
- `disabled`

本轮规则：

1. 图片初始导入状态为 `pending`
2. 当存在活跃任务时可置为 `assigned`
3. 当业务判断该图已完成标注时置为 `completed`
4. 人工停用置为 `disabled`

### 4.2 新增 `annotation_tasks` 表

确定字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL PK | 任务 ID |
| `image_id` | BIGINT NOT NULL | 图片 ID |
| `user_id` | BIGINT NOT NULL | 用户 ID |
| `status` | VARCHAR(16) NOT NULL | `assigned/submitted/expired/cancelled` |
| `assigned_at` | TIMESTAMPTZ NOT NULL | 分配时间 |
| `expires_at` | TIMESTAMPTZ NOT NULL | 过期时间 |
| `submitted_at` | TIMESTAMPTZ NULL | 提交时间 |
| `created_at` | TIMESTAMPTZ DEFAULT NOW() | 创建时间 |

确定索引：

1. `INDEX idx_tasks_user_status (user_id, status)`
2. `INDEX idx_tasks_image_status (image_id, status)`
3. `INDEX idx_tasks_expires_at (expires_at)`

本轮不加：

- `UNIQUE (user_id, image_id)`

原因：

1. 当前已由 `scores` 表的唯一约束保证最终结果不重复
2. 预留未来人工回收后再次分配的可能性

### 4.3 `scores` 表调整

确定新增：

1. `task_id BIGINT NULL`

用途：

1. 结果可追溯到任务
2. 便于后续排查“任务已分配但未提交/重复提交”等问题

保留现有唯一约束：

- `UNIQUE (user_id, image_id)`

## 5. 后端接口确定改动

### 5.1 新增 `POST /api/tasks/next`

确定行为：

1. 接口用于获取当前用户的下一张任务
2. 如果用户已有未过期且未提交的任务，优先返回最早分配的那个
3. 如果用户当前只有 1 个任务且没有 `nextTask`，允许再发 1 个新任务
4. 如果用户已有 2 个活跃任务，不再发新任务
5. 如果系统没有可分配图片，返回 `task: null`

接口返回固定字段：

1. `task_id`
2. `image_id`
3. `image_url`
4. `object_key`
5. `assigned_at`
6. `expires_at`

### 5.2 新增 `POST /api/tasks/{task_id}/submit`

确定行为：

1. 仅接收单张任务评分提交
2. 服务端必须校验任务归属和过期状态
3. 合法请求写入 Redis 队列
4. 任务状态更新为 `submitted`

请求体固定字段：

1. `image_id`
2. `aesthetic_score`
3. `completeness_score`

### 5.3 旧接口保留但降级

本轮兼容期内保留：

1. `/api/images/batch`
2. `/api/score`

但原则上：

1. 新前端不再调用它们
2. 旧接口只用于过渡

### 5.4 `/api/my-stats` 保留

确定保留不改协议。

只改前端调用时机，不改接口本身。

## 6. Worker 确定改动

### 6.1 Redis 队列消息结构调整

当前消息仅包含：

1. `image_id`
2. `user_id`
3. `aesthetic_score`
4. `completeness_score`

本轮确定新增：

5. `task_id`

### 6.2 落库后处理

worker 处理成功后：

1. 向 `scores` 表写入 `task_id`
2. 按插入成功结果更新 `images.score_count`
3. 根据业务阈值决定是否更新 `images.status`

本轮先采用的简单规则：

1. 插入评分成功后，`images.score_count += 1`
2. 当 `score_count >= 1` 时，将图片标记为 `completed`

说明：

这与当前系统“每张图只需要 1 次有效评分”的逻辑一致。

## 8. 任务分配规则确定版

本轮任务分配采用以下固定规则：

### 8.1 活跃任务定义

满足以下条件之一的任务视为活跃任务：

1. `status = 'assigned'`
2. `expires_at > NOW()`

### 8.2 单用户上限

每个用户最多允许 2 个活跃任务：

1. 当前任务 1 个
2. 预取任务 1 个

### 8.3 分配顺序

`/api/tasks/next` 调用时按以下顺序处理：

1. 先把当前用户已过期的 `assigned` 任务标记为 `expired`
2. 查询该用户未过期的 `assigned` 任务
3. 若已有任务，优先返回最早分配且尚未提交的任务
4. 若用户活跃任务数小于 2，则尝试分配新的 `pending` 图片
5. 无图可分配时返回 `task: null`

### 8.4 图片选择规则

本轮图片选择规则固定为：

1. 从 `images.status = 'pending'`
2. 且 `deleted = FALSE`
3. 且不存在未过期 `assigned` 任务
4. 随机选 1 张

说明：

这比当前简单的 `score_count = 0 ORDER BY RANDOM() LIMIT 10` 更适合单图链路。

## 11. 验收标准确定版

改造完成后，必须满足以下条件才算通过：

1. 用户点击开始后，请求的是 `/api/tasks/next` 而不是 `/api/images/batch`
2. 页面主状态不再包含 10 张批次数组
3. 前端最多只预取 1 张下一张图片
4. 图片请求地址为对象存储/CDN 地址，而不是业务后端图片代理地址
5. 提交评分后不会同步等待 `/api/my-stats`
6. 提交成功后能立即进入下一张
7. 用户离开页面后，未提交的预取任务能在过期后重新分配
8. 管理后台统计仍可正常工作

## 12. 开发顺序建议

实际执行时，按以下顺序推进：

1. 先改表结构和模型
2. 再补新 API
3. 再补 worker
4. 最后切前端
5. 稳定后清理旧接口

这样可以保证：

1. 每一步都可单独验证
2. 兼容期内线上可控
3. 避免前端先切但后端支撑还没就绪

---

## 13. 最终执行结论

本次改造的确定版策略是：

1. 保留对象存储直连
2. 引入真实任务表
3. 后端新增单图任务接口
4. 前端只维护 `currentTask + nextTask`
5. 评分提交仍走 Redis 异步落库
6. 每用户最多持有 2 个活跃任务
7. 统计改为乐观更新 + 定时校准
8. 先不做缩略图系统

后续开发应以本文为准，不再回到“批量还是单图”“URL 还是 object_key”“是否需要任务表”这几个基础方向上反复摇摆。
