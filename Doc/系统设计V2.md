# Muse Scoring Platform — 系统设计文档 V2

> 本文档对齐当前系统现状，覆盖当前已上线架构、数据模型、单图任务分配链路、无 Redis 直写数据库方案、管理员导出功能以及 R2 扫桶入库方案。

---

## 一、系统概述

**项目定位**：面向公众的图片双维度评分平台。用户对图片从“美学表现”和“细节完成度”两个维度进行 1-10 分评分，管理员可查看进度、用户排行，并导出当前已标注数据。

**当前设计目标**：
- 支持对象存储中海量图片的批量入库
- 浏览器直连对象存储加载图片，避免业务后端承载图片流量
- 单图展示、单图提交、最多预取 1 张下一张
- 评分结果直接写入 PostgreSQL，降低运行依赖
- 支持管理员一键导出当前已标注数据

## 三、当前核心设计原则

### 3.1 图片永远直连对象存储

后端只返回图片元数据和可访问 URL：
- `task_id`
- `image_id`
- `image_url`
- `object_key`
- `assigned_at`
- `expires_at`

浏览器中的 `<img>` 直接请求 R2 公网域名，不经过业务后端。

### 3.2 单图展示 + 最多预取 1 张

当前评分页只展示 1 张图片。  
前端在用户查看当前图时，后台最多再申请并预加载 1 张下一张。

### 3.3 一轮固定 10 张

虽然是单图展示，但前端仍然以“本轮 10 张”为用户体验单位：
- 顶部进度条按 10 张推进
- 第 10 张完成后进入本轮完成页
- 不会无限分配图片给用户

### 3.4 评分结果直接写数据库

当前版本已移除 Redis 队列。  
评分接口直接写 PostgreSQL，并同步更新：
- `scores`
- `images.score_count`
- `images.status`
- `annotation_tasks.status`

## 五、数据库设计（当前版本）

### 5.1 images — 图片主表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL PK | 图片 ID |
| `r2_url` | TEXT | 图片公网 URL |
| `object_key` | TEXT | R2 中的对象 key |
| `public_url` | TEXT | 当前用于浏览器访问的 URL |
| `status` | VARCHAR(16) | `pending / assigned / completed / disabled` |
| `score_count` | INTEGER | 已被成功打分的次数 |
| `deleted` | BOOLEAN | 软删除 |
| `created_at` | TIMESTAMPTZ | 创建时间 |

### 5.2 annotation_tasks — 任务分配表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL PK | 任务 ID |
| `image_id` | BIGINT FK | 对应图片 |
| `user_id` | BIGINT FK | 分配给谁 |
| `status` | VARCHAR(16) | `assigned / submitted / expired / cancelled` |
| `assigned_at` | TIMESTAMPTZ | 分配时间 |
| `expires_at` | TIMESTAMPTZ | 任务过期时间 |
| `submitted_at` | TIMESTAMPTZ | 提交时间 |
| `created_at` | TIMESTAMPTZ | 创建时间 |

### 5.3 scores — 评分结果表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL PK | 评分记录 ID |
| `image_id` | BIGINT FK | 图片 ID |
| `user_id` | BIGINT FK | 用户 ID |
| `task_id` | BIGINT | 来源任务 ID |
| `aesthetic_score` | INTEGER | 美学分 |
| `completeness_score` | INTEGER | 完成度分 |
| `submitted_at` | TIMESTAMPTZ | 提交时间 |

数据库唯一约束：
- `UNIQUE (user_id, image_id)`

这保证了同一用户对同一图片不会重复记分。

### 5.4 audit_exports — 导出审计表

记录管理员每次执行导出的行为：
- 谁导出的
- 导出格式
- 导出记录数
- 导出时间

## 六、当前打分主链路

### 6.1 获取任务

接口：

```text
POST /api/tasks/next
```

行为：
1. 校验登录态
2. 可选校验 Turnstile
3. 先过期当前用户已超时任务
4. 再纠正图片状态
5. 若已有未过期任务，则优先返回
6. 否则从可分配图片中分配 1 张

### 6.2 展示图片

前端拿到 `image_url` 后：
- 当前页立即展示当前图
- 背景最多预取 1 张下一张
- 图片始终由浏览器直连 R2

### 6.3 提交评分

接口：

```text
POST /api/tasks/{task_id}/submit
```

行为：
1. 校验任务归属、状态、过期时间
2. 直写 `scores`
3. 更新 `images.score_count`
4. 将图片状态设为 `completed`
5. 将任务状态设为 `submitted`

### 6.4 兼容旧接口

当前仍保留：
- `POST /api/images/batch`
- `POST /api/score`

主要用于兼容旧路径或调试，不是当前主链路。

## 九、R2 图片导入方案

当前系统提供两种图片入库方式：

### 9.1 import_images.py

适合场景：
- 图片还在本地目录
- 需要一边上传到 R2，一边写入数据库

### 9.2 sync_r2_to_db.py

适合场景：
- 图片已经全部在 R2
- 只需要把对象 key 和公开链接批量同步到数据库

这是正式数据导入的推荐方案。

工作方式：
1. 列出指定 bucket / prefix 下所有图片对象
2. 按 `object_key` 判断数据库中是否已存在
3. 批量插入新记录
4. 批量更新旧记录的 `r2_url/public_url/status`

默认批大小：
- `1000`

可通过环境变量调整：
- `R2_SYNC_BATCH_SIZE`

## 十一、当前已知设计特点与边界

1. 当前版本已完全弃用 Redis
2. 当前评分结果直接入 PostgreSQL
3. 当前图片状态会在任务分配时做动态纠正
4. 当前导出功能走“全量已标注数据导出”
5. 当前正式数据导入推荐走 `sync_r2_to_db.py`

## 十二、后续建议

对于正式投产后的下一步优化，建议优先考虑：

1. 为 `images.object_key` 增加唯一索引
2. 给导出功能补上时间范围筛选
3. 将图片状态纠正逻辑从“请求时补偿”收敛为更稳定的状态机
4. 为大规模 R2 导入增加导入日志和断点续跑能力

---

## 十三、总结

当前系统已经完成从早期“本地图片 + Redis 异步写库”向“R2 对象存储 + 单图任务分配 + PostgreSQL 直写 + 管理员导出”的演进。

当前正式可用主链路是：

```text
R2 图片对象
  -> sync_r2_to_db.py 批量写入 images 表
  -> 用户请求 /api/tasks/next
  -> 浏览器直连 R2 加载图片
  -> 用户提交评分
  -> FastAPI 直写 PostgreSQL
  -> 管理员后台查看数据并导出当前已标注结果
```

这就是当前版本与系统现状对齐后的 V2 设计。
